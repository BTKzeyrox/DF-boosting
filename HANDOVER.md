## 3 sexies. Accès selon l'heure du shift + suivi sur la page Employés (2026-10-08, demandes de BTK, « GO » donné)
**Accès.** Un booster ne peut se connecter que pendant son shift (jour ou nuit selon sa fiche), **contrôlé côté serveur** (`shiftAccess` / `inShiftWindow` dans `df-api/index.ts`, heure de Madagascar UTC+3, heures lues dans les Réglages, cache 60 s). La fenêtre = shift **élargi** de `access_before_min` avant le début et de `access_after_min` après la fin (60 et 60 par défaut, **réglables** dans Réglages > « Accès et suivi des boosters » ; sans rapport avec `late_tolerance_min`, qui ne sert qu'au calendrier). Le shift de nuit passe minuit ; une fenêtre ≥ 24 h = toujours ouvert. Champ `access_mode` sur l'utilisateur : absent = **auto** (fenêtre ci-dessus), `allow` = toute heure, `block` = jamais. Un booster avec une **session en cours** (début ou fin à valider) garde l'accès jusqu'à sa fin. À la connexion : 403 + message (`code: 'shift'`, il indique l'heure d'ouverture) ; pendant l'usage : 401 avec ce code, le site déconnecte et la page de connexion affiche le message (`sessionStorage` `df_login_notice`). L'admin n'est jamais concerné. Admin : liste déroulante « Accès » sur chaque ligne de `EmployeesManagement.tsx` (`db.setAccessMode`).

**Page Employés.** Nouvelle colonne « Activité » : statut en direct (`getPresenceStatus` : Hors ligne / Connecté sans poste / En poste / Sans poste), temps connecté du jour, et **pastilles « à valider »** (Début, Fin, Avance, Profil) qui disparaissent dès la décision ; cliquables (`setValFilterIntent` + navigation vers Validations au bon filtre).

## 3 quinquies. Photos : Cloudinary (2026-10-07)
- **Pourquoi** : Supabase gratuit = 1 Go de fichiers. BTK n'a pas d'argent : R2 et Firebase demandent une carte. Cloudinary gratuit : 25 crédits/mois partagés (1 crédit = 1 Go de stockage ou de transfert), sans carte.
- **Comment** : la route `upload` de `df-api` envoie les **images** à Cloudinary (envoi signé, serveur à serveur, dossier `df-proofs/`) et renvoie l'URL `https://res.cloudinary.com/dirnrsy5v/image/upload/...`. Si Cloudinary échoue : repli sur Supabase Storage. PDF et texte restent sur Supabase Storage. Les anciennes photos restent sur Supabase.
- **Clés** : Cloud name `dirnrsy5v` (public, écrit dans le code). La clé API et le **secret** sont dans le **coffre-fort Supabase** (`vault.secrets` : `cloudinary_api_key`, `cloudinary_api_secret`, `cloudinary_cloud_name`), lus par la fonction SQL `public.df_get_secret(name)` réservée au `service_role` et limitée aux noms `cloudinary_%`. Ne jamais mettre ces valeurs dans le repo. **BTK a collé le secret dans le chat : lui demander de le régénérer sur Cloudinary (Settings > API Keys) et de remplacer la valeur dans le coffre-fort** (`select vault.update_secret(id, 'nouvelle valeur')`).
- **Nettoyage** : seules les **photos de preuve** sont supprimées automatiquement, après `retention_days` (défaut **7 jours**, réglable dans Réglages). Jamais effacés : calendrier, sessions, paie, avances, messages, demandes d'inscription/mot de passe/profil, même refusées. Le nettoyage supprime les photos Cloudinary (`destroy`) et Supabase, marque `proofs_purged`, traite 60 sessions par passage, toutes les 2 heures, déclenché par n'importe quel appareil connecté. Si une suppression Cloudinary échoue, la session est réessayée au passage suivant.
- **Limites à connaître** : liens publics (toute personne qui a l'URL voit la photo) ; les images de la messagerie et les photos de profil vont aussi sur Cloudinary et ne sont pas nettoyées (peu de place) ; Cloudinary compte aussi le transfert dans les 25 crédits.
- **Testé le 2026-10-07** : envoi d'une photo de preuve (booster de test) → fichier présent dans Cloudinary (`df-proofs/…`, 127 Ko).
